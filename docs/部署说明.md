# GitHub 与网站部署说明

核对日期：2026-10-22。当前仓库保存可运行的本机 MVP，尚未上线公网。

## 可以如何使用 GitHub

| 方式 | 能否运行完整系统 | 适用情况 |
|---|---|---|
| GitHub 仓库（当前公开） | 保存、管理代码与课程资料 | 已在使用；仓库中不包含学生数据库与 API 密钥 |
| GitHub Pages | 不能 | 仅适合另做静态介绍页或无后端的页面演示 |
| GitHub Actions + 云服务器 | 可以，在完成公网适配后 | 提交代码后自动检查并发布，服务持续运行在云服务器上 |
| 支持后端及持久磁盘的平台 + GitHub 集成 | 可以，在完成平台适配后 | 平台从仓库构建并运行服务，需保留数据库和密钥文件 |

GitHub Actions 负责部署流程，网站运行在选定的服务器或托管平台上；不能用一次 Actions 运行来代替长期的网站服务。

GitHub 官方资料：[GitHub Pages 的静态托管范围](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)、[通过 GitHub Actions 持续部署](https://docs.github.com/en/actions/get-started/continuous-deployment)。

## 当前项目为什么不能直接上传 Pages

- 前端依赖同站点 `/api/` 接口，登录、班级、学生、课程与规划都通过后端处理。
- `app/server.mjs` 目前监听 `127.0.0.1`，只允许本机 Host，并按本机 HTTP 地址检查请求来源。将文件上传到 Pages 不会创建这些接口。
- 后端需要 Node.js 24+ 和 SQLite；导出 PDF 需要 Python、ReportLab 及能正常显示中文的字体。
- `app/.data/` 存储数据库、会话和加密密钥。GitHub 仓库没有这些运行数据，代码自动更新也不能覆盖这些数据。

## 完整部署的实施顺序

1. 确定服务器或托管平台、访问域名及数据保存位置。先使用单实例和持久磁盘，适配当前 SQLite 架构。
2. 增加显式的线上配置：监听地址、平台分配的端口、允许的域名与 HTTPS 访问来源。本机模式继续保持现有默认值。
3. 配置 HTTPS 入口和与其匹配的会话 Cookie；保留请求来源检查。开放入口前，由负责人完成首次管理员初始化。
4. 准备 Node.js、Python 和中文字体，验证在线 PDF 导出。将数据库与 `master.key` 一同存放在持久目录，设置备份和恢复方式。
5. 在 GitHub 配置目标平台所需的部署凭据，运行自动检查，再部署服务。凭据不提交到仓库。
6. 用测试账号检查登录、老师班级权限、学生管理、规划保存、20天 NOIP 排期与 PDF 导出，并验证重启后数据仍然保留。

当前只完成部署方式核对与实施说明，未配置云服务器、部署凭据、自动发布工作流或公网域名。下一步需要确定实际托管目标，才能针对其入口、存储及运行环境完成适配。
